# 自動検証の計画

単体テスト448件が通っていても、実際に画面を見ると問題が出る。
**何を自動で見つけられるようにするか**を決める文書。

---

## 1. これまでのバグは何だったか

単体テストを増やしても捕まらなかったものを並べる。ここから検査の種類を決める。

| # | バグ | 種類 | 単体テストで捕まるか |
|---|---|---|---|
| 1 | 課題の詳細・コメントが Markdown 描画されない | **繋ぎ忘れ**（部品はあるのに使っていない） | 捕まらない |
| 2 | プロジェクト画面20のうち12でサイドバーが無い | **書き写しの取りこぼし** | 捕まらない |
| 3 | マイルストーンの開始日を入れる欄が無い（案内文は「設定で入れて」と言う） | **案内と機能の不一致 / CRUD不完全** | 捕まらない |
| 4 | 課題一覧で期限切れが赤くならない（ダッシュボードでは赤い） | **同じ意味の表示が画面で不揃い** | 捕まらない |
| 5 | バーンダウンの既定が終わったマイルストーン（空グラフ） | **既定値の選び方** | 捕まらない |
| 6 | Y軸の目盛りが `1,1,1,0,0` | **退化データ（0件）** | 捕まる（実際に足した） |
| 7 | ガントの日付が重なる | **レイアウト崩れ** | 捕まらない |
| 8 | ボードが接続前でも「接続していません」 | **初期状態の見せ方** | 捕まらない |
| 9 | 本番の worker が `zod` 欠落で起動しない | **本番構成でのみ起きる** | 捕まらない（ビルド検算を足した） |
| 10 | Discord への webhook が全部 400 | **外部連携の形式不一致** | 捕まる（実際に足した） |
| 11 | IP宛にSNIが来ずTLSが失敗 | **本番構成でのみ起きる** | 捕まらない |

**11件中8件が単体テストの外側。** 内訳は大きく3つ:

- **A. 繋ぎ目の抜け**（1・2・3・4）— 部品や画面の間で揃っていない
- **B. 実際に動かさないと見えない**（5・6・7・8）— 既定値・退化データ・見た目
- **C. 本番構成でのみ起きる**（9・11）— 開発環境では再現しない

## 2. 何を作るか

### A. 静的検査（コードを読んで機械的に突き合わせる）

`scripts/check-consistency.mjs` を1本作り、下の検査をまとめて実行する。
**CIが無いので `pnpm check` で手元から回す。**

| 検査 | 何を見るか | 捕まえられたバグ |
|---|---|---|
| **A1 サイドバーの有無** | `src/app/projects/**` と課題詳細の `page.tsx` が `<Shell>` に `project=` を渡しているか | #2 |
| **A2 CRUDの完全性** | マスタ（version / category / issueType / status / customField / webhook / team / user / repository）ごとに `add*` `update*` `delete*` が揃っているか。欠けは表に出す | #3 |
| **A3 案内文と機能の対応** | 「〜で入れてください」「〜で設定してください」という文言を抽出し、**指している画面にその入力欄（`name=`）が実在するか** | #3 |
| **A4 共有部品の使用漏れ** | 利用者が書いた本文を出している箇所（`issue.description` / `activity.content` / `wikiPage.content` / `pr.body`）が `<Markdown>` を通っているか | #1 |
| **A5 表示の揃い** | 期限日を出している画面が、期限切れの色分けを持っているか | #4 |
| **A6 本番依存の検算** | 既にある `docker/check-worker-deps.mjs` をここからも呼ぶ | #9 |

> A3 が効くのは、**案内文が仕様の宣言になっている**から。
> 「設定で入れてください」と書いた時点で、その入力欄があることが約束になる。

### B. 動的検査（実際に画面を開いて確かめる）

`scripts/check-screens.mjs`（ヘッドレスChrome）。3つの観点を回す。

| 検査 | やること | 捕まえられたバグ |
|---|---|---|
| **B1 全ルートが開く** | 32画面すべてで HTTP・JSエラー・error boundary を確認（実施済みを仕組みにする） | — |
| **B2 退化データ** | **課題0件のプロジェクト（INF）**と、マイルストーン0件・メンバー1人の状態で全画面を開く | #5 #6 |
| **B3 レイアウト崩れ** | 隣り合うラベルの矩形が重なっていないか／`scrollWidth > clientWidth` で文字が切れていないか。ガントで作った判定を全画面に広げる | #7 |
| **B4 権限の分離** | 10人のデモユーザーで主要画面を開き、**参加していないプロジェクトの名前が本文に出ていないか**を突き合わせる | （M4の権限漏れの再発防止） |
| **B5 フォームの往復** | 主要フォームを送信し、保存されること・エラー時にメッセージが出ること・**画面が飛ばないこと**を確認 | （SPA化の回帰） |

### C. 本番構成での検査

`scripts/check-prod.sh`。**開発環境では再現しない種類**をここで潰す。

- 本番イメージをビルド（`check-worker-deps` が走る）
- 別スタックで起動し、**7サービスが running で留まる**（`restarting` を見落とさない）
- HTTPS + IP直打ちで `/login` が 200（SNIの件）
- 課題作成→検索ヒット→添付の往復

## 3. やる順番

**効果の大きい順。** A は数時間、B は半日、C は既存の手順をまとめるだけ。

| 段 | 内容 | 目安 | 理由 |
|---|---|---|---|
| 1 | **A1〜A5** の静的検査 | 半日 | いま出ているバグの4件を機械的に見つけられる。実行が速く、毎回回せる |
| 2 | **B1・B2・B3** の画面検査 | 半日 | 退化データとレイアウトは目視では見落とす |
| 3 | **B4・B5** | 半日 | 権限は漏れると影響が大きい。SPA化の回帰も固定したい |
| 4 | **C** 本番構成 | 2時間 | 移設前に1回通せばよい。毎回は要らない |

`package.json` に入れる:

```
pnpm check         # A（静的・数秒）
pnpm check:screens # B（画面・数分）
pnpm check:prod    # C（本番構成・十数分）
```

---

## 4. 自動化しないもの（正直に線を引く）

機械には判断できないので、**見つけたら人に報告する**形にする。

- **「本家と同じか」** — 一次情報に記述が無い項目は判定できない（ガントのヘッダがこれ）
- **意匠の良し悪し** — サイドバー下部の緑の余白のような「変に見える」は判定できない
- **文言の自然さ**
- **業務として正しいか** — 例えばバーンダウンの計算式が現場の感覚に合うか

これらは画面を見て報告する。**検査が通っても「バグが無い」ことにはならない。**

---

## 5. 見つけたバグの扱い

1. まず**再現する検査を足す**（先に失敗させる）
2. 直す
3. 検査が通ることを確認
4. `docs/00-spec-verified.md` に判断が要るものは決定として記録

CLAUDE.md のルール1（憶測で埋めない）はそのまま。
検査が「おかしい」と言っても、**正しい姿が一次情報から決まらないなら
`TODO(要確認)` にして止める。**
