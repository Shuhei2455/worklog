# 実装ロードマップ

各フェーズは Claude Code の1〜3セッションで終わる粒度に切ってある。
**受け入れ条件を満たすまで次のフェーズに進まない。** 満たしたら `docs/PROGRESS.md` に日付と実際にかかった作業内容を追記する。

---

## フェーズ0: 土台

### タスク
- [ ] `docker compose` 一式（app / worker / postgres / redis / meilisearch / gitea / caddy）
- [ ] Prisma スキーマ全テーブル定義（`01-design.md` 4章のすべて。この時点で全部書く）
- [ ] シード投入: 標準状態4件・優先度定数・完了理由定数・管理者ユーザー1件
- [ ] Auth.js によるログイン（Credentialsプロバイダ）
- [ ] `can(user, action, resource)` の骨格と単体テスト
- [ ] プロジェクトのCRUD、参加ユーザーの追加・削除、プロジェクト管理者フラグ
- [ ] プロジェクト設定画面（機能ON/OFF、種別・カテゴリー・バージョン・状態のマスタ管理）

### 受け入れ条件
- `docker compose up` だけで全コンテナが起動し、ログインしてプロジェクトを作れる
- 状態の並べ替えを試すと、Openより前とClosedより後には置けないことがUIで確認できる
- `pnpm test` で権限関数のテストが通る

### 注意
スキーマは**この段階で全部書く**。後から追加していくと、活動履歴や通知のように既存レコードの移行が必要な部分で手戻りする。テーブルは作るがUIは作らない、という状態で構わない。

---

## フェーズ1: 課題管理コア

### タスク
- [ ] 課題の登録・編集・削除（keyId 採番はトランザクション内 `UPDATE ... RETURNING`）
- [ ] 課題詳細画面（コメント + 変更履歴を `activities` から時系列で混ぜて表示）
- [ ] 変更差分の日本語ラベル解決関数
- [ ] 添付ファイルのアップロード・ダウンロード
- [ ] 親子課題（1階層制約のバリデーション込み）
- [ ] 関連課題
- [ ] 課題一覧: フィルタ条件の正規化関数、一覧表示、ソート、ページング
- [ ] 検索条件の保存
- [ ] ダッシュボード（自分が担当・自分が登録・最近見た課題）

### 受け入れ条件
- 自分ひとりで実務のメモを課題として1週間運用できる
- フィルタ条件を組み替えてもURLで共有でき、リロードで復元される
- 課題を並列で10件同時作成しても keyId が重複しない（テストを書く）

### 注意
**フェーズ1が終わったら、機能を足す前に自分で毎日使い始めること。** 使わずに積み上げると、一覧のデフォルト表示やソート順といった体感を左右する部分の判断を全部間違える。

- 週次の進捗確認をこのアプリだけで済ませられる

## フェーズ4: Git連携

### タスク
- [ ] Gitea へのユーザー同期
- [ ] リポジトリ作成とwebhook自動登録
- [ ] push webhook 受信 → 課題キー抽出 → コメント自動登録
- [ ] ブランチ名の課題キーからPR作成時に関連課題を自動紐づけ
- [ ] リポジトリ閲覧UI（ファイルツリー・内容・コミット一覧・差分）
- [ ] プルリクエスト一覧・詳細の表示

### 受け入れ条件
- コミットして push すると、該当課題にコメントが自動で付く
- 課題からコミット、コミットから課題の双方向に辿れる
- `link_commits_to_issues` をOFFにすると連携が止まる

### 注意
キーワードによる状態変更（`#fix` / `#close`）は**実装しない**。本家が廃止した機能であり、誤操作で状態が飛ぶと信頼を失う。

## 進め方の約束

1. 1フェーズ = 1ブランチ。フェーズ名をブランチ名にする（`phase-1-issues`）
2. 受け入れ条件を満たしていない状態でフェーズを閉じない
3. 仕様で迷ったら `00-spec-verified.md` を見る。書いていなければ `TODO(要確認)` を残して**その場で決めずに報告する**
4. スキーマ変更は必ず Prisma のマイグレーションファイルとして残す。`db push` で済ませない
5. 各フェーズの終わりに `docs/PROGRESS.md` を更新する
