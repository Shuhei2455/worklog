# 職場VMへの移設マイルストーン（M6〜M11）

手順そのものは `docs/04-deploy.md` にある。この文書は**それをどの順で通し、
どこで手を止めてレビューするか**を決めるもの。

開発の M0〜M5 と同じ流儀で、**受け入れ条件とレビューを通らないマイルストーンは閉じない**。

---

## ルール1の読み替え（重要）

CLAUDE.md ルール1は「**本家Backlogの仕様**と比較するレビュー」を求めている。
移設には比較する本家仕様が無いので、**省略せず、比較の相手を置き換える**。

| | 開発（M0〜M5） | 移設（M6〜M11） |
|---|---|---|
| 一次情報 | developer.nulab.com / support-ja.backlog.com | **職場VMでの実測**（コマンドの出力・画面・ログ） |
| 着手前レビュー | 仕様書の該当章を読み、足りない仕様を洗い出す | **確認すべき前提を列挙し、実測できないものはユーザーに依頼して止まる** |
| 完了時レビュー | 差分表（一致 / 意図的に相違 / バグ） | 差分表（**一致 / 意図的に相違 / 不具合**）。判定は同じ3値 |
| 「おおむね動いた」 | 禁止 | **禁止**。数字か画面で示せないものは未確認として残す |

変えないもの:

- **不具合が1件でもあればマイルストーンを閉じない**
- ルール2（Gitタグ `mN` と Obsidian ノートの**両方**）はそのまま
- 憶測で埋めない。分からなければ `TODO(要確認)` を残して止まる

## 全体像

| M | 名前 | 主眼 | 環境への依存 | 失敗したときの影響 |
|---|---|---|---|---|
| M6 | 持ち込み物の準備 | 自宅側で完結させる | なし | 作り直せる |
| M7 | VMの前提確認と起動 | VMが要件を満たすか | **大** | VMの手配やり直し |
| M8 | コア機能の疎通 | 課題管理が回るか | 小 | ここが通らなければ全部止まる |
| M9 | 環境依存機能の疎通 | プロキシ・SMTP・ポート | **最大** | **3点とも機能の縮退で回避できる**（後述）。移設自体は止まらない |
| M10 | 残りの機能の疎通 | 検索・添付・API・Git・権限 | 小 | 個別に潰せる |
| M11 | 運用開始 | バックアップと試用 | 中 | 運用開始を遅らせる |

### 順序の理由

M8 を M9 より先にするのは、**SSE やメールを試すには先に課題が作れる状態が要る**ため。
ただし M9 の3点（SSE・SMTP・Gitのポート）は
**M8 が通った直後にすぐ見る。**運用準備に時間をかける前に、
環境の事実を確定させたい。

## M6 持ち込み物の準備（自宅側）

VMに触る前に、自宅側で完結する作業を全部終える。
ここは何度でもやり直せるので、**完全に通ってから職場へ持ち込む**。

### 着手前に確認すること

- [ ] 上げる版のタグを決める（例 `0.8.3`）。職場の `.env` の `APP_IMAGE_TAG` と揃える
- [ ] GitHub のリポジトリ名と所有者を決める（**public**）
- [ ] ghcr.io 用の PAT を作る（`write:packages`）
- [x] 自宅のデータを持ち込むか → **新規で始める**（2026-09-14 に決定）。`seed` を使う
- [x] 持ち込み経路 → **GitHub のクローン**（ファイル運搬なし）

> [!info] M7 の前提確認が軽くなった
> 以前は「VMにファイルを持ち込めるか」が最大の関門だったが、
> クローン方式にしたので **VMが github.com と ghcr.io に出られること**
> だけが前提になった。ユーザーが確認済み。

### 手順

`docs/04-deploy.md` の 1章。

```bash
cd ~/docker/backlog-clone

# 1回だけ: ghcr.io にログイン（PATに write:packages）
echo <PAT> | docker login ghcr.io -u <GitHubのユーザー名> --password-stdin

# ビルドして ghcr.io へ上げる（アプリ＋サードパーティ5つ）
GHCR_OWNER=<ユーザー名> APP_IMAGE_TAG=0.8.3 scripts/push-images.sh

# GitHub へ push
git remote add origin https://github.com/<ユーザー名>/backlog-clone.git
git push -u origin main --tags

# 外部通信の確認
scripts/egress-check.sh
```

そのあと **GitHubで各パッケージを public にする**（VMの認証が不要になる）。

### 受け入れ条件

| # | 条件 | 示し方 |
|---|---|---|
| 1 | 本番イメージがビルドできる | 型エラー0で完了する（**開発コンテナで `pnpm build` はしない**） |
| 1-b | **ワーカーの依存の検算が通る** | ビルド中に `[worker-deps] すべて解決できた` が出る |
| 1-c | **ワーカーが実際に起動する** | `logs worker` に「検索インデックスと webhook の配信を待機します」 |
| 2 | **6つのイメージが ghcr.io に上がっている** | `https://github.com/<ユーザー名>?tab=packages` に6件 |
| 3 | **6つとも public になっている** | 認証なしで `docker manifest inspect ghcr.io/<ユーザー名>/postgres:16-alpine` が通る |
| 4 | GitHub に push できている | `git log origin/main -1` が手元と一致 |
| 5 | **秘密情報が入っていない** | `.env` が追跡外・履歴にも無い／`caddy/certs/*` が無視されている |
| 6 | **クリーンなクローンからビルドできる** | 別ディレクトリに clone して `docker build` が通る |
| 7 | 自宅で**別スタック**を ghcr.io の名前で起動できる | 7サービスが healthy / Up |
| 8 | 外部通信が github.com / ghcr.io 以外に無い | `egress-check.sh` |

> 条件6を入れているのは、**`.gitignore` が効きすぎてビルドに必要な物が
> 欠ける**ことがあるため。手元では動くのにクローンでは落ちる、という形で出る。
> 実際に確認したら通った（2026-09-14）。

### 完了時レビュー

| 項目 | 期待 | 実測 | 判定 |
|---|---|---|---|
| イメージ容量 | | | |
| tar.gz の sha256 | | | |
| 別スタックでの起動 | 7サービス healthy/Up | | |
| **worker が running で留まる** | restarting にならない | | |
| 復元後の件数 | 16項目一致 | | |
| 外部接続 | 0件 | | |

> [!failure] ここで実際に不具合が1件出た（2026-09-14・`docs/04-deploy.md` にも記録）
> **本番の worker が起動しなかった。** `zod` が `/worker` の依存に無く、
> `ERR_MODULE_NOT_FOUND` で再起動を繰り返していた。
> M5 でカスタム属性（`src/lib/custom-field.ts` が zod を使う）を入れたときから
> 壊れていたが、**M5 の検証では worker の状態まで見ていなかったため通っていた**。
>
> 影響: 検索インデックスの更新・webhook の配信・メール送信が動かない。
> 画面は動くので気づきにくい。
>
> 原因は `/worker` の依存を**手で並べたリスト**から作っていること
> （pnpm の node_modules はシンボリックリンクの塊で COPY できないため）。
> 同じ種類の漏れは **M3-e で `bullmq`、今回 `zod` の2回目**。
>
> 対策として `docker/check-worker-deps.mjs` を追加し、ビルド段で
> **入口から import を実際に辿って依存を検算する**ようにした。
> 欠けていればビルドが落ちるので、起動時まで持ち越されない。
>
> **教訓: `ps` が Up でも worker は見る。** 「7サービス起動」を
> healthy の数だけで判定すると、restarting を見落とす。

## M7 VMの前提確認と起動

**VMの実物に初めて触る段。** ここで前提が欠けていると後が全部崩れるので、
構築の前に必ず実測する。

### 着手前に確認すること（実測してから進む）

```bash
docker --version && docker compose version   # Compose は v2 が要る
nproc && free -h && df -h /                  # CPU / メモリ / 空き容量
date && timedatectl | grep -i zone           # 時刻と時間帯
ss -lntp | grep -E ':(80|443|2222)'          # 使う予定のポートが空いているか
```

要件は**本番構成を実際に起動して測った値**から出している（測定条件は下の表の後）。

| 項目 | 必要な値 | 根拠 | 満たないときどうするか |
|---|---|---|---|
| Docker | あること | — | VM管理者に依頼。**要件はこれだけ**（Node も pnpm も不要） |
| Docker Compose | **v2**（`docker compose`、ハイフン無し） | — | v1 だと `docker-compose.prod.yml` が通らない |
| CPU | **2コア以上**（4コア推奨） | 20並列の負荷で app が **117%**（1コアを超える） | 1コアだと一覧の表示が詰まる |
| メモリ | **2GB以上**（4GB推奨） | アイドル **344MiB** / 20並列で **442MiB** | 実測に対して余裕はあるが、Postgres のキャッシュに回す分を見て2GB |
| 空き容量 | **10GB以上**（添付を多用するなら20GB） | イメージ計 **1.6GB** / 課題1533件でDB **84MB** | バックアップを7世代持つと添付ぶんが効く |
| 時間帯 | `Asia/Tokyo` | — | ずれていると期限日と「期限切れ」の判定が1日ずれる |
| ポート | 80(HTTP) と 2222(Git SSH) | `docker-compose.prod.yml` | 公開するのは**2つだけ**。塞がれていたら M9 で判断 |
| 再起動後の自動起動 | Docker が enabled | — | VMの再起動でアプリが上がってこない |

## M9 環境依存機能の疎通（最大のリスク）

職場のネットワークが相手なので、**自宅では確かめられなかった3点**。
M8 が通ったらすぐここへ来る。

### 9-a. SSE（ボードのライブ更新）

`docs/04-deploy.md` 3章 #9。

```bash
# プロキシを通して event-stream が流れるか。ヘッダだけ見れば足りる
curl -sN -D- -o/dev/null --max-time 5 \
  "http://<ホスト>/api/projects/<KEY>/events" -H "Cookie: <セッション>"
# → Content-Type: text/event-stream が返り、接続が切れずに保たれること
```

確認: 2つのブラウザで同じボードを開き、片方で課題をドラッグ →
もう片方が数秒で追従する。

> [!info] **これは設計変更を伴うリスクではない**（2026-09-14 に実装を確認）
> `EventSource` を使っているのは `BoardClient.tsx` の**1箇所だけ**で、
> 用途はボードの `issue.moved` のみ。`es.onerror` で `live=false` に落ちる
> 作りなので、**切られてもボードは通常どおり動く**（ライブ更新が止まるだけ）。
>
> 代替が必要なら、同じファイルに一定間隔の `router.refresh()` を足す（10行程度）。
> 他の画面は SSE を使っていないので影響しない。
>
> よって**SSEが通らなくても移設は止めない。** 判定は「意図的に相違（機能を縮退）」。

切られている場合の対処（この順に試す）:

1. プロキシ側で `/api/projects/*/events` のバッファリングを無効にする
2. それが通らなければポーリングに切り替える（要コミット・M9内で対応）

## M11 運用開始

機能が揃ったあと、**運用として続く形にする**段。

### 受け入れ条件

| # | 条件 | 示し方 |
|---|---|---|
| 1 | バックアップが自動で回る | cron か systemd timer を仕込み、**翌日ファイルが増えているのを確認** |
| 2 | バックアップの保存先がVMの外 | 同じディスクに置くと、ディスクが死んだとき一緒に消える |
| 3 | **復元のリハーサルをした** | 別ディレクトリに復元して件数一致を確認。**本番を止めずに** |
| 4 | 管理者パスワードの復旧手段を確認した | `set-password` で変更できる |
| 5 | 2〜3人で1週間試用した | 出た要望と不具合を記録する |
| 6 | 5〜20人での応答を見た | 一覧・ボード・検索の体感。**いまは1人でしか測っていない** |
| 7 | 運用の引き継ぎメモがある | 誰が何を見るか（ログ・バックアップ・版上げ） |

> 条件3を入れているのは、**取れているつもりのバックアップが戻らない**のが

### HTTPS × IP直打ちで踏んだ落とし穴（実機で再現・対処済み）

> [!failure] IPアドレス宛には **SNI が送られない**
> SNIはホスト名専用とRFCで決まっており、**ブラウザも curl も
> IPアドレス宛にはSNIを送らない**。SNIが無いと Caddy は出す証明書を選べず、
> **TLSハンドシェイクの段階で internal error** を返す。
>
> 画面には「安全な接続を確立できません」としか出ないので原因が分からない。
> `openssl s_client -servername <IP>` では通ってしまうため、
> 「証明書は正しいのにブラウザだけ繋がらない」という形で現れる。
>
> 対処: `caddy/Caddyfile.prod` のグローバル設定に `default_sni {$APP_HOST}`。
> **これが無いと職場で全員が繋がらない。**

> [!warning] 公的なCAはIPアドレスに証明書を出さない
> 選べるのは2つだけ:
>
> | | 設定 | ブラウザの警告 | git clone |
> |---|---|---|---|
> | Caddy内蔵のローカルCA | `CADDY_TLS=internal` | **出る** | **失敗する**（要CA配布） |
> | 社内CA発行 | `CADDY_TLS="/etc/caddy/certs/tls.crt /etc/caddy/certs/tls.key"` | 出ない | 通る |
>
> `internal` のままだと `git clone` が
> `server certificate verification failed` で落ちる（実機で確認）。
> 各PCにルート証明書を配れば解消するが、**社内CAに発行してもらうのが本筋**。
>
> 発行を依頼するときは **subjectAltName にIPを入れてもらう**こと。
> CNだけの証明書は今のブラウザが受け付けない。
> （Caddy内蔵CAは正しく `IP Address:` のSANを付ける。実機で確認済み）
>
> - [ ] `TODO(要確認)`: 社内CAに**IP宛の証明書**を出してもらえるか。
>       出してもらえないなら Caddy内蔵CA＋ルート証明書の配布になる

## いま分かっている未確認事項（着手前に潰すもの）

移設を始める前に、ユーザー側で確認が必要なもの。
**これが埋まらないと M6 や M7 で止まる。**

**上の8項目は 2026-09-14 に全部回答済み**（「確定した構成」を参照）。
残っているのは次の1つだけ。

| # | 確認すること | 止まるM | なぜ重要か |
|---|---|---|---|
| 1 | **社内CAがIPアドレス宛の証明書を出してくれるか**（subjectAltName にIP） | M7 | 出してもらえないなら Caddy内蔵CAになり、**全PCへのルート証明書の配布**と、**開発者のgit設定**が必要になる。作業量が変わる |

出してもらえない場合にやること:

1. `CADDY_TLS=internal` のまま進む
2. Caddy のルート証明書を取り出して配る
   ```bash
   docker compose -f docker-compose.prod.yml exec caddy \
     cat /data/caddy/pki/authorities/local/root.crt > kadai-root.crt
   ```
3. 各PCの証明書ストアに入れてもらう（ブラウザの警告が消える）
4. Git を使う人は、あわせて次のどちらかが要る
   ```bash
   git config --global http.sslCAInfo /path/to/kadai-root.crt
   # または OS の証明書ストアに入れる
   ```
