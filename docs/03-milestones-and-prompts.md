# マイルストーンとプロンプト集

`docs/03-milestones-and-prompts.md` として配置する。

---

## 事前準備（1回だけ）

`CLAUDE.md` の「ルール2」内の `<OBSIDIAN_VAULT>` を実際のパスに置き換える。

```
例: /Users/xxx/Documents/ObsidianVault
    /mnt/nas/obsidian
```

Vaultがリポジトリの外にある場合、Claude Code がそのパスに書き込める必要がある。起動時のディレクトリより上位にあると拒否されるので、その場合は起動オプションで許可するか、Vaultへのシンボリックリンクをリポジトリ内に置く。

---

## マイルストーン一覧

各マイルストーンは、以下の**3つのゲート**をすべて通過して初めて完了とする。

1. 受け入れ条件（`docs/02-roadmap.md`）をすべて満たす
2. 完了時レビューの差分表で**バグ0件**
3. Gitタグ `mN` とObsidianノートの両方を記録

| # | 名前 | 中身 | 目安 |
|---|---|---|---|
| M0 | 土台 | docker compose一式、Prismaスキーマ全定義、認証、権限関数、プロジェクトCRUD、マスタ管理 | 2〜3セッション |
| M1 | 課題管理コア | 課題CRUD、keyId採番、コメントと変更履歴の統合表示、添付、親子課題、関連課題、一覧とフィルタ、ダッシュボード | 3〜4セッション |
| M2 | 見せ方と通知 | ボード（DnD・並び順・SSE）、ガント（表示条件4パターン）、通知3経路、ウォッチ、スター | 3〜4セッション |
| M3 | Wiki・検索・API | Wiki、ファイル共有、Meilisearch、メール通知、webhook送信、API v2 | 3〜4セッション |
| M4 | Git連携 | Giteaユーザー同期、リポジトリ作成、push webhook、ブランチ名連携、リポジトリ閲覧UI、PR表示 | 2〜3セッション |
| M5 | チーム展開 | カスタム属性、チーム、CSV入出力、バーンダウン、監査ログ、バックアップ手順 | 3〜4セッション |

**M1が終わったら、M2に進む前に自分で毎日使い始めること。** 使わずに積み上げると、一覧の初期表示やソート順といった体感を左右する部分の判断を全部間違える。

## プロンプト1: 初回セッション

```
CLAUDE.md と docs/ 配下の資料をすべて読んでください。

特に CLAUDE.md の「絶対に守る2つのルール」は、他のどの指示よりも優先してください。
このプロジェクトでは、仕様を憶測で埋めた結果、過去に7箇所の設計ミスが発生しています。

読み終えたら、M0に着手する前に次の4点を報告してください。コードはまだ書かないでください。

1. 【着手前レビュー】M0のスキーマ定義に必要な仕様のうち、
   docs/00-spec-verified.md に書かれていないものはどれか。
   一次情報で確認できるものは確認し、確認できないものは私への質問として列挙してください。
2. docs/01-design.md のデータモデルをPrismaに落とす際に解釈の幅が出る箇所
   （リレーションの持ち方、複合キー、インデックス、カスケード削除）
3. M0を何セッションに分けるのが妥当か、その分割案
4. Obsidian Vault のパスが CLAUDE.md に設定されているか。
   未設定なら、私に聞いてください。
```

## プロンプト2: マイルストーン着手（毎回使う）

```
docs/PROGRESS.md を読んで現状を把握してください。

これから M<N> に着手します。CLAUDE.md ルール1の「着手前レビュー」を実行してください。

1. M<N> で作る機能に関係する docs/00-spec-verified.md の章を読み直す
2. 実装に必要なのに仕様書に無い項目を洗い出す
3. 一次情報で確認できるものは確認し、docs/00-spec-verified.md に追記する
4. 確認できないものは列挙して私に聞く

洗い出しの報告を受けてから実装に入ります。今はまだコードを書かないでください。
```

## プロンプト3: 実装中に仕様で迷ったとき

```
それは docs/00-spec-verified.md に書かれていますか。
書かれていないなら、憶測で決めずに TODO(要確認) を残して止まってください。
本家の挙動を確認できる出典があるなら、先にそれを提示してください。
```

---

## プロンプト4: マイルストーン完了時

```
M<N> の受け入れ条件を満たしたと判断したら、CLAUDE.md ルール1の「完了時レビュー」を実行してください。

1. M<N> で実装した機能を、本家Backlogの仕様と1項目ずつ突き合わせる
2. 差分表を作る。判定は「一致 / 意図的に相違 / バグ」の3値のみ
3. 「おおむね一致」は使わない。理由が書けない相違はバグとして扱う
4. バグが1件でもあれば、修正してレビューをやり直す

バグ0件になったら、まだタグは打たずに差分表を私に見せてください。
```

差分表を確認したあとで:

```
差分表を承認します。CLAUDE.md ルール2の記録を実行してください。

1. docs/PROGRESS.md に日付・所要セッション数・詰まった点を追記
2. git commit と git tag m<N>
3. Obsidian の <VAULT>/10_Projects/backlog-clone/M<N>-<名前>.md を
   CLAUDE.md のテンプレートどおりに作成
4. backlog-clone-index.md にリンクを追加

Obsidianアプリを開いている場合は、書き込む前に教えてください。
```

## プロンプト5: セッションが長くなってきたとき

```
ここまでの作業を docs/PROGRESS.md に「M<N> 途中」として記録し、
次のセッションで再開するために必要な情報（未完のタスク、判断待ちの項目、
動かない状態のファイル）を書き出してください。
コミットはしますが、タグは打たないでください。
```

---

## うまくいかないときの対処

**レビューが形骸化してきたら**（差分表が「一致」ばかりになる）

```
その差分表は本家のドキュメントを実際に参照して作りましたか。
参照した出典URLを項目ごとに示してください。
示せない項目は「未確認」に分類し直してください。
```

**Obsidianへの記録を飛ばしたら**

```
CLAUDE.md ルール2は Git と Obsidian の両方が必須です。
Obsidianノートを作成するまで M<N+1> には着手しません。
```

**仕様を憶測で埋め始めたら**

```
今の判断の根拠は docs/00-spec-verified.md の何章ですか。
書かれていないなら、それは憶測です。TODO(要確認) に戻してください。
```
